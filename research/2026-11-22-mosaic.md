# 2026-11-22 — Planar mosaic targets (artarget "walk around the surface")

## v1 (ORB, center-distance keyframes)
Field test (Behrang, M13): only ~2 views ever added, even on patterned surfaces.
Reproduced on a synthetic **dim, low-contrast walk-around** clip (camera circles the table, oblique ~0.35 trapezoid, view rotates 360°):
v1 → 4 views, lost tracking 3 of 9 checks.

Root causes
1. Keyframe rule = "center moved > 0.28·frame size". Walking *around* a table keeps the view centered on the table → no new keyframes, while the viewing direction changes a lot → matching to the top-down reference fails → lost.
2. ORB with default FAST threshold finds few corners on dim/low-contrast frames.

## v2 (implemented in artarget)
- CLAHE (clip 2.5, 8×8) on gray before ORB; FAST threshold 20 → 10; 1500 features.
- `USAC_MAGSAC` instead of plain RANSAC for the homography.
- Coverage grid (20 px cells in mosaic space): keyframe when the view adds > 22 % new surface **or** looks at known surface from a new direction (> 26°) or distance (scale < 0.72 or > 1.4) — this is what panorama/stitching pipelines do (overlap-based keyframes), adapted to a translating camera.
- Match against nearest-3 keyframes + reference + latest keyframe.
- Manual "+ view" button.
- Tiles for MindAR chosen by diversity in position **or** viewing direction (up to 6).
Result on the same clip: **13 views, never lost**, 6 tiles, mosaic covers ~1.6× more area.

## Panorama knowledge to borrow next
| Technique (from stitching pipelines) | Why | Status |
|---|---|---|
| Overlap-based keyframes | add views that bring new content or new viewpoint | done (v2) |
| Local contrast normalization (CLAHE) | more stable features in dim light | done (v2) |
| Global bundle adjustment / loop closure over all keyframes | removes drift that accumulates when chaining homographies (visible skew at mosaic edges) | Proposed |
| Exposure compensation + seam finding / multi-band blending | cleaner mosaic, fewer false features at seams | Proposed (low priority for tracking) |
| Better features than ORB (SIFT/AKAZE in desktop OpenCV; learned: XFeat/LightGlue) | viewpoint/scale robustness | Phase 1 (XFeat) — current opencv.js build has no SIFT/AKAZE |

Note: 360° panoramas assume a **rotating** camera (homography = K·R·K⁻¹); a table mosaic is a **translating** camera over a plane (general homography). Different model — the rotation-only model is the right one for a future "stand in place and scan the room" mode (also gives an HDRI/IBL for lighting the model).

Reference projects: OpenCV `stitching` module / `stitching_detailed` sample (Apache-2.0), Hugin (cpfind + optimizer, GPL), OpenMVG (MPL-2.0), COLMAP (BSD).
